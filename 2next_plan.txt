一、当前目标

以开源项目 infinite-canvas 为主要参考，对 ImageX 做一次有依据的产品与交互审计：

1. 先实际查看参考项目的代码、文档和可运行界面，梳理值得借鉴的交互、信息架构、媒体工作流与技术实现。
2. 对照 ImageX 现状，找出不合理、重复、难理解、维护成本高或缺乏实际价值的功能和结构，提出删除、合并或重做建议。
3. 补上对 ImageX 用户确有价值、且符合本地优先定位的能力；不为追求功能数量而堆叠控件。
4. 最后加入“生成视频”模式，模式顺序必须是：文生图 → 图生图 → 生成视频 → 工作流。

参考项目及本轮实际查阅资料：
- GitHub：https://github.com/basketikun/infinite-canvas （main 分支）
- 仓库元数据确认许可证为 MIT；本轮可经 GitHub API 和 raw 文件访问。曾有短暂连接失败，后续已成功读取。
- `README.md`：项目定位、核心功能、运行方式、前端直连及本地数据说明。
- `docs/content/docs/overview/features.mdx`：画布项目、节点工作流、AI 能力、素材、同步和当前限制。
- `docs/content/docs/canvas/canvas-node-manual.mdx`、`canvas-shortcuts.mdx`：节点生成路径、引用关系、快捷操作及视频任务说明。
- `web/src/components/canvas/`、`web/src/lib/canvas/`、`web/src/pages/canvas/`：无限画布、节点、连线、画布状态和交互实现目录。
- `web/src/pages/video/index.tsx`、`web/src/services/api/video.ts`、`web/src/components/video-settings-panel.tsx`：视频生成页面、服务请求和参数 UI。当前只检查了关键服务实现与页面入口，后续可继续沿具体流程读完整代码。
- `web/package.json`：参考项目使用 React/Vite，并包含 Zustand、localforage、Axios、fflate、React Router 等；不意味着 ImageX 应整体替换自身依赖栈。
- 本轮没有实际启动参考项目，也没有逐一操作其线上演示；交互视觉验收仍需补做，不能把文档能力等同于当前线上可用性。

参考项目已确认的特点（仅记录，不等于决定照搬）：
- 以项目为单位保存无限画布；支持节点拖拽、缩放、连线、选择、分组、撤销/重做、复制粘贴、导入导出和小地图。
- 节点包含文本、图片、视频和生成配置；文本、参考素材与生成节点通过连线表达上下文，批量结果可组织成关联节点并保留生成参数以便重试。
- 视频由独立页面和 API service 管理。文档列出 OpenAI 兼容 `POST /v1/videos`、`GET /v1/videos/{id}`、`GET /v1/videos/{id}/content`；Gemini 路径为 `predictLongRunning` 加 operation 轮询。创建后的任务 ID 保存到视频节点以支持刷新后继续轮询。
- 视频服务实现还提供可取消的轮询、结果存储、可选参考图片/视频/音频，以及模型脚本扩展点；这些是参考项目的能力，不是通用 API 保证。
- 功能文档提到浏览器本地项目/素材数据、可选 WebDAV 同步、提示词来源、插件和本地 Canvas Agent。它们会扩大产品及安全范围，不预设为 ImageX 本轮必做。
- 参考项目处于活跃开发状态，其 README 明示数据格式可能变化；借鉴数据模型时要独立设计迁移，不能直接依赖其未稳定格式。

二、工作原则

- 先研究、盘点、提出有证据的取舍，再分阶段改代码；不要在未检查参考项目前直接重做主界面。
- “去除没有必要的东西”需要说明判断依据、影响范围和替代路径。删除前检查其对现有任务、记录、设置、导出、键盘操作和测试的影响。
- 保留有明确使用价值的能力，尤其是本地优先、用户自带 API 凭证、多供应商、请求取消、图像编辑、结果留存和产品套图流程；若认为要调整或移除，先解释收益和迁移影响。
- 借鉴交互和架构思路，不直接复制代码、品牌、文案或资产。检查参考项目许可证及其依赖许可证；若考虑复用代码，先确认许可证兼容性并保留要求的声明。
- 不改变纯浏览器直连服务商的隐私边界，不上传用户 API Key、提示词、图片或任务记录到 ImageX 自建服务。
- 供应商视频 API 并非统一标准。不得假设 OpenAI 图像协议或某家服务商自动兼容视频；先调查参考项目和用户可用服务商的真实协议，再确定 adapter 与设置项。没有确认协议前，不发起会扣费的真实请求。
- 每个阶段保持可运行、可验证；未经用户明确要求，不自动 commit、push、发布或打部署包。
- 保留工作区已有改动，不回退用户文件，不读取或输出 `codepup_api.txt`、`error.txt` 等敏感资料。

阶段 2：ImageX 产品与代码审计

1. 盘点主界面每个模式、主要设置、重复入口、错误/空状态、移动端布局和数据流。
2. 盘点生成/编辑/工作流共用部分与不应共用部分，检查当前状态管理、请求模型、缓存、协议层及组件边界。
3. 形成保留、合并、删除、重做、补充五类清单。对删除项说明使用场景、删除理由及对历史数据和配置的迁移方案。
4. 优先解决能减少流程摩擦或维护复杂度的问题；不做纯视觉翻新或无证据的大规模重写。
5. 提交实施前的短决策记录：本阶段做什么、不做什么、验收标准和风险。涉及不可逆数据删除或会改变凭证/隐私边界的决定必须先取得用户确认。

第一轮审计与实施决策（2026-10-05）：
- 不整体迁移到无限画布。ImageX 的核心是高频单图/批量生成、编辑和套图任务队列；无限画布的项目、边、分组和撤销历史会大幅增加概念及持久化复杂度，并与已有请求/套图历史重叠。借鉴其清楚的任务来源、参数快照和长任务恢复，不复制整套节点编辑器。
- 保留现有的图片队列与产品套图，不删除现有设置和历史。源码里仍有旧 Responses/Completions/private 类型和归一化逻辑；它们虽不在当前主 UI，但承担旧配置/记录兼容，贸然删除有数据迁移风险。等确认读取用途及兼容窗口后再清理，不把“代码看起来旧”当作无意义的证据。
- 生成视频作为独立任务工作台接入共享模式导航，但视频结果和视频文件不伪装成图片请求。首版聚焦纯文本提示词生成视频，不扩展图生视频、音频参考、插件或无限画布。
- 已实现：主导航加入“生成视频”（位于图生图后、工作流前）；新增供应商级可选视频模型、独立生成面板、OpenAI 兼容 `/v1/videos` 创建/轮询/content 下载、取消本地轮询、IndexedDB 视频 Blob 存储及 localStorage 任务元数据恢复。
- 首版限制：只支持 OpenAI 兼容协议的纯文本视频生成；时长暂为 4/8/12 秒，尺寸暂为 16:9、9:16、1:1 的 720p 档。Gemini 视频、参考图/音频、供应商特定字段、服务端取消尚未接入；须先按目标供应商文档逐项验收。
- 参考项目视频实现确认可作为协议适配起点：OpenAI 风格 `/videos` 创建、按 task ID 查询并下载 content；Gemini `predictLongRunning`/operation 查询。供应商能力不统一，因此需由用户明确配置视频模型，真实生成前显示协议和目标供应商；不为默认内置供应商预填视频模型。
- 任务 ID、提示词、模型、参数和状态保存在浏览器本地；视频媒体 Blob 放 IndexedDB。刷新后恢复轮询；取消请求只中止本地轮询/下载，不声称服务端生成一定会停止，除非其 API 明确支持取消。

当前初步对照方向（待完整审计后决定取舍）：
- 值得评估：把提示词、参考图、生成配置、结果和重试关系可视化；结果保留足够生成元数据；任务可取消且异步任务刷新后可恢复；在一个工作区内连续探索多个方案。
- 不预设照搬：将整个 ImageX 改为无限画布、插件系统、Codex/本地 Agent、WebDAV 云同步、外部提示词源或音频/视频/语言模型全模态平台。这些明显超出“精简现有 ImageX 并加入生成视频”的必要范围，应以用户真实需求和维护成本为依据。
- ImageX 当前已经有结果队列、编辑参考图、历史、槽位批次及本地持久化；需先找出现有痛点，避免重复造一套节点历史。
- 主模式顺序是明确需求，不因参考项目的路由/页面结构而改变：文生图 → 图生图 → 生成视频 → 工作流。

阶段 3：产品与架构调整

1. 按审计结论逐项实施。先做可独立验证的小改动，再调整共享架构。
2. 统一跨模式的任务生命周期和结果呈现时，保留文生图、图生图、视频任务之间必要的输入、参数、预览及结果差异。
3. 若建立 provider adapter，明确能力声明、鉴权、同步/异步提交、轮询、取消、结果提取和错误映射；不在通用 API 文件里累积供应商特例。
4. 所有设置和历史升级必须向后兼容；删除旧功能前保留必要的数据读取/迁移，不静默丢弃本地记录。

阶段 4：生成视频模式

进度：首版代码已接入，待启动开发服务器后做导航与布局检查，并需要用户配置真实支持 `/v1/videos` 的供应商进行端到端验收。

模式位置：文生图 → 图生图 → 生成视频 → 工作流。

实施前置条件：
- 确认至少一个目标服务商的官方或可验证视频生成 API 文档、鉴权方式、请求字段、异步任务流程、轮询/取消方式、结果地址有效期和 CORS 行为。
- 说明服务商/模型能力差异，哪些字段通用、哪些由 adapter 提供；没有依据的参数不得展示为通用参数。
- 若没有可验证协议，先完成产品交互原型和可测 adapter 契约，将真实请求集成列为外部阻塞，不模拟成功或默认接入虚构 endpoint。

功能范围与验收：
- 视频提示词输入和模式切换；仅在 API 确认支持时提供图生视频/参考图输入，不把纯文本生成视频与图生视频混为一种能力。
- 按供应商能力暴露时长、画幅/分辨率、画面比例等参数；校验取值，切换模型时避免遗留不支持参数。
- 统一请求列表中的排队、运行、成功、失败、取消状态；异步轮询不能重复提交已扣费任务，并清晰展示耗时和服务商错误。
- 成功后可播放预览、查看基本元数据、下载视频；处理临时 URL 过期和大文件，避免把完整视频 Base64 长期放入 localStorage。
- 刷新页面后的恢复行为要有明确设计；若无法恢复供应商任务，显示真实限制，不伪造继续状态。
- 适配移动端、键盘和可访问性；中文/英文文案齐全。
- 至少覆盖 adapter 单元测试、轮询/取消/超时测试、结果展示组件测试和三种生成模式顺序的 UI 测试。
