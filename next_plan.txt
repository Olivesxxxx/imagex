二、项目概况

1. 产品定位

ImageX 基于 CPA Image，是一个本地优先的 OpenAI 兼容图像生成与编辑控制台。它是纯浏览器前端，不包含业务后端，也不在项目服务器保存用户数据。浏览器直接请求用户配置的 OpenAI 或兼容 API。

2. 当前主要能力

- 文生图：调用 /v1/images/generations。
- 图片编辑：调用 /v1/images/edits，支持本地选择、粘贴图片和复用历史结果，最多 5 张输入图。
- Responses 生图：调用 /v1/responses，并使用 image_generation 工具。
- Chat Completions 生图：调用 /v1/chat/completions，并使用 image_generation 工具。
- 连接测试：调用 /v1/models。
- 批量与队列：单次最多创建 100 个请求；并发度 1-100；请求间隔 0-3600 秒；支持取消、过滤和清理。
- 结果处理：兼容 URL/base64 图片结果，支持单图下载、历史结果再次编辑、响应 JSON 查看和完成图片 ZIP 导出。
- 本地工作流：保存设置、生成/编辑各自的 Prompt 草稿与历史、Prompt 置顶、请求摘要和请求详情。
- 国际化：中文和英文，语言状态体现在 URL 路径。
- SEO/静态部署：Vite 构建后执行预渲染，仓库包含 robots、sitemap、manifest、Netlify headers/redirects 和 SEO CI 检查。

3. 技术栈

- React 19 + TypeScript 6
- Vite 8
- Tailwind CSS 4
- shadcn/ui 风格组件，底层使用 Radix UI
- Vitest + Testing Library + jsdom
- lucide-react 图标，sonner 消息提示
- 无服务端数据库、无鉴权服务、无环境变量依赖

4. 核心代码结构

- src/App.tsx：三栏主界面及各类确认/进度/JSON 对话框的组合入口。
- src/hooks/use-image-console.ts：核心运行状态；负责队列调度、请求执行、取消、结果缓存、下载和界面动作。目前约 68 KB，是后续维护风险最高的单体模块。
- src/lib/image-console.ts：领域类型、默认设置、参数校验、四类请求载荷、响应解析、缓存模型和格式化工具。目前约 58 KB。
- src/lib/api.ts：HTTP 请求、Bearer 鉴权、JSON/文本响应解析和错误转换。
- src/lib/endpoints.ts：从用户填写的 Base URL 规范化五类直连端点。
- src/lib/storage.ts：localStorage 与 IndexedDB 持久化、迁移和清理。
- src/lib/request-queue.ts：并发数、请求间隔和下一任务调度规则。
- src/components：生成参数、请求列表、结果区、设置窗口和基础 UI 组件。
- src/lib/*.test.ts、src/App.test.tsx：领域逻辑、存储、队列、端点、结果和主要交互测试。

5. 数据与安全边界

- localStorage 保存设置、Prompt 草稿和 Prompt 历史。
- IndexedDB 数据库名为 ImageX，保存请求摘要、响应详情和图片缓存。
- API Key 默认只保存在当前运行内存；只有用户启用“记住 API Key”后才写入 localStorage，存储时没有加密。
- ImageX 不提供请求中转代理，目标 API 必须正确配置 CORS。
- 纯前端架构意味着浏览器 CORS 是硬约束，也无法真正隐藏 API Key。若未来面向多用户或公网部署，应新增自有后端/BFF，而不是继续把密钥放在浏览器。

6. 当前已知问题与技术风险

- npm audit 报告 2 个 high：vite 间接依赖 postcss@8.5.15，jsdom 间接依赖 undici@7.27.2；均显示 fixAvailable=true。它们主要位于开发/测试工具链，但仍需升级和回归。
- use-image-console.ts 和 image-console.ts 体积过大，UI 状态、业务编排、请求适配及缓存逻辑耦合，新增功能时容易扩大回归面。
- 当前只配置一个 Base URL/API Key，再用四个模型字段切换；不支持多个供应商配置、快速切换、模型自动发现或供应商级参数差异。
- OpenAI 兼容接口实际返回结构差异较大。当前已有多种响应提取兼容逻辑，但缺少明确的 provider adapter 边界和真实服务契约测试。
- 队列仅存在单浏览器实例中；刷新后的 queued/running 请求会如何恢复需作为验收项重点检查，不能视作服务端可靠任务队列。
- ZIP 为项目自行实现的浏览器端打包逻辑，大批量/大图片时可能产生较高内存占用。
- 没有端到端浏览器测试；现有测试以单元和组件测试为主，真实 CORS、下载、IndexedDB、刷新恢复和响应图片加载仍需人工或 Playwright 覆盖。
- Git 远程应只指向 ImageX 自有仓库；上游来源通过 README 与 MIT License 说明。

阶段 2：明确二开需求和产品边界

在编码前，按优先级确认以下问题：

1. 使用对象：仅自己本机使用，还是团队/公网多用户使用。
2. API 来源：只接 OpenAI，还是还要接中转站、Azure OpenAI、Gemini/Vertex、火山、阿里云等兼容或非兼容接口。
3. 数据策略：只保存在当前浏览器，还是需要账号、云同步、跨设备和共享图库。
4. 核心增强：供应商预设、模型列表、参数模板、Prompt 模板、任务重试、图片管理、元数据检索、批量编辑等，确定第一版真正必需的范围。
5. 部署方式：本地 Vite、静态站、桌面应用（Tauri/Electron），还是前后端服务。

建议第一版优先做“多供应商配置 + 可靠的任务重试 + 可检索图库”，因为它们直接改善日常生图工作流；账号体系、云端协作和复杂画布应在确认确有多人需求后再引入。

阶段 5：做标记来重新生图（下一阶段核心功能）

目标：在当前生成图片上直接标记不满意或缺失的区域，并将图片与标记说明作为一次新的图生图请求输入。该功能仍保持纯浏览器前端，原图、标记和请求数据只保存在当前浏览器。

1. 入口与交互
   - 在当前生成图片右上角操作区增加“做标记来重新生图”按钮，使用编辑/标注语义的图标。
   - 点击后打开标注工作区；原有“作为参考图”和旋转按钮继续保留，功能不互相覆盖。
   - 标注完成后可取消、清空、撤销/重做，并预览最终提交效果。
   - 标注工作区在桌面端和移动端都必须保持图片比例、工具栏可操作和按钮不遮挡画布。

2. 第一版工具范围
   - 画笔：可调笔刷大小，支持橡皮擦或清除局部标记。
   - 箭头：拖拽起点和终点，支持调整粗细。
   - 矩形/圆形：用于圈选问题区域，支持调整边框粗细。
   - 文字：点击画布定位后输入说明，支持移动、删除和基础字号设置。
   - 选择工具：选中、移动、删除已有标注，避免只能按创建顺序修改。

3. 数据与请求设计
   - 原图作为底图，标注层独立存储，避免破坏原始生成图片。
   - 提交前在浏览器中合成带标注的参考图，并保留原图、标注 JSON、合成图之间的关联。
   - 将用户补充说明与原提示词分开显示，提交时生成明确的编辑提示词；不得静默覆盖原提示词。
   - 复用现有图生图队列、取消、失败处理、历史记录和本地缓存，不新增服务端存储。
   - 明确不同 OpenAI 兼容服务对 mask/透明区域/带标记图片的支持差异；第一版优先兼容无需 mask 的“带标记参考图 + 提示词”流程，并为后续 mask 输出保留扩展点。

4. 推荐实现顺序
   - 先抽取独立的 `annotation-canvas` 组件和标注模型，完成画布缩放、坐标换算、撤销/重做。
   - 再实现画笔、箭头、矩形/圆形、文字四类工具及移动端触控事件。
   - 增加合成导出、透明背景/mask 预览和图生图请求适配。
   - 接入历史记录与结果卡片，支持从任意已完成图片再次进入标注工作区。
   - 最后补充大图性能、键盘快捷键、无障碍标签和 Playwright 交互测试。

5. 验收标准
   - 四类标注可以创建、移动、删除，撤销/重做结果稳定。
   - 标注不会改变原始图片；取消编辑不会产生新请求。
   - 提交后生成一条新的图生图任务，原任务与新任务可区分并能复用提示词。
   - 刷新页面后，已保存的标注任务不会丢失或污染其他请求详情。
   - 桌面端/移动端无按钮遮挡、坐标偏移或画布溢出；类型检查、测试、构建和真实兼容 API 冒烟全部通过。
